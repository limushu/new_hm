# 案件档案与办理流程

## 业务边界

一个案件档案对应同一委托或争议。档案承载案情摘要、类型标签、当事人、日程、待办、工作记录和收支；内部可以有多个诉讼或非诉办理流程，例如一审、二审、执行、合同审查、专项顾问。新建档案不自动生成任何流程。同类流程可以重复建立，通过独立 ID、案号和显示序号区分。

流程不是案件状态。看板上的“未开始 / 进行中 / 已结案”等状态属于整个档案，可由用户自定义；某个流程办结不会自动关闭整个档案。

1.1.3 起，案件状态和类型标签共用可输入、联想、明确创建及复用的交互，但不混用语义：状态为单选、决定看板归列；类型标签为多选、用于分类搜索。状态名称创建或改名不得与其他状态重名（忽略大小写），旧库已有重复项不自动合并；只调整其颜色仍允许。标签移除仅解除此案关联，保留候选。联想默认优先已有项，用户可明确选择“创建”添加不同名称。

## 三个独立维度

| 维度 | 含义 | 保存位置 |
| --- | --- | --- |
| 案件状态 | 整个委托或争议的管理状态 | cases.status_id |
| 流程 | 一个具体办理过程，有独立案号、法院、法官、材料与阶段 | proceedings |
| 流程内阶段 | 当前流程内部的工作进展，如立案、举证、开庭 | stages，按 position 排序 |

每个流程有“办理中 / 已办结”生命周期。多个流程可以同时办理。每个案件最多指定一个“当前关注”的办理中流程，用于概览和看板摘要；查看另一个流程只是页面浏览，不会修改当前关注。办结当前关注流程后清空关注，用户再自行选择，不推测另一个流程应当接手。

流程内阶段以 stages 的 current 行为准；proceedings.stage 保留旧版兼容摘要。阶段名称允许用户自定义，不硬编码为必须遵循的法律流程，也不根据阶段名称自动结案。已办结流程保留历史，不允许继续切换阶段，恢复办理后可继续调整。

1.1.1 起，阶段排序只用于展示与办理参考，不构成只能向前的强制状态机。各阶段可为“待办理 / 当前办理 / 已完成 / 已跳过”，同一流程最多一个当前阶段。切换当前阶段将原当前阶段转为待办理，绝不自动标记完成；完成由用户明确操作。任意中间阶段均可从已完成或已跳过重新打开为待办理，不重置其他阶段的完成状态，也不抢占另一个当前阶段。重新设为当前则明确切换当前关注点。

变更记录是按发生时间追加的历史，最新在前；状态完成、重开与当前阶段切换记录原状态和目标状态。重复保存相同状态不产生重复记录，旧记录保留且不被重开覆盖。旧版自动标记的完成状态保留，无法替用户判断是否确实完成；用户可以主动重开。

1.1.4 起，办理中的流程允许删除任意阶段，包括当前阶段，也可删除至没有阶段后重新添加。删除当前阶段会清空 stages 当前项与 proceedings.stage 摘要，不自动指定接手阶段，不改变流程关注、流程生命周期、案件状态或其他阶段的完成状态。删除与历史记录在同一事务保存，剩余阶段位置连续重排；既有变更历史、流程事件和流程材料不随阶段删除。已办结流程沿用只读规则，恢复办理后再调整。

## 办理路径

顶部始终列出本案全部流程，包括历史流程。节点显示当前阶段或已办结、案号，并用关注图标标出当前关注流程。点击节点进入该流程详情。

parent_id 表示用户确认的“承接自”，只能引用本案另一个流程，禁止自引用和循环。多个流程可以承接同一前序流程，表达并行分支。它不是自动推演的诉讼路线，也不是 Git 的提交合并模型；当前每个流程只有一个前序。

新增流程时明确展示前序选项，可选择独立流程。新增的流程成为当前关注，已有流程仍保持原生命周期。旧数据升级后不猜测前序，不根据一审、二审、执行名称拼接假历史。

## 概览与详情

- 概览回答：争议和目标是什么、有哪些流程、当前关注什么、正在做什么、接下来有哪些安排、涉及哪些人、材料如何分布。
- 流程详情回答：这个流程的案号和承接关系、法院和法官、内部办理阶段、流程事项及阶段变更历史。
- 概览中的人员展示本案共用关联及当前关注流程的法院、法官；其余流程的人员在对应流程详情查看。
- 自动阶段切换记录属于历史，默认折叠；人工流程事项单独展示，不让操作日志占据案件首页。

## 共享数据与归档

日历与案件概览读取同一 calendar_events 记录，以 case_id 关联。通用日历创建时不预选案件；从案件详情主动添加时预选当前案件，用户仍可修改或取消。编辑同一日程不复制记录。流程事项仅在用户勾选“同时加入此案件的日历”时生成对应日程，避免把全部操作日志当作日程。

材料归档支持案件共用、具体流程两个正式范围，页面明确标注导入目标。更细的阶段可通过该流程下的文件夹组织；当前没有 stage_id 自动归档，不声称自动跟随阶段移动文件。概览中的范围入口直接打开对应材料范围。

案件类型改为可复用的 #标签。tag_catalog 持久保存用户已创建的名称，case_tags 保存赋予具体案件的关系；移除某案标签或删除该案不会丢失候选名称。旧版 case_type 仅保留存储兼容，不再承担分类语义，也不决定是否建立流程。

## 数据升级与校验

数据库版本 5 增加流程生命周期、明确前序、事件分类和标签表。升级前对旧版本建立 SQLite 检查点备份，迁移处于事务内；已有案号、法院、法官和阶段保留，历史前序保持未指定。旧版明确格式的自动阶段事件分类为 stage_change，不删除历史。

后端 hm-core 是规则边界：校验同案承接、禁止循环、标签规范、关注流程生命周期及完成后阶段锁定。React 负责浏览状态和呈现；预览适配器只用于开发，不替代真实 SQLite 迁移验证。

## 1.2 委托关系与流程身份

案件档案保存稳定的当事人：名称、与我方关系（我方委托人 / 对方当事人 / 其他参与人）、服务身份（代理、辩护、法律顾问等可自定义）及可选联系对象。可不建立独立联系对象，先填写名称；也可在已选流程中先记身份，稍后补姓名。选择已有对象建立反向案件关系，无需再重复添加。

诉讼或业务身份属于具体流程：同一委托人一审为原告，二审可以是被上诉人，执行为申请执行人。三个身份分别记录；新增流程不继承、不猜测身份。输入时联想已有值及常用身份，允许自定义。概览以案件“当前关注”的流程显示身份；详情以正在浏览的流程显示身份，浏览不改变关注。

历史“原告”等普通联系人关联不自动转换成“我方委托人”，因为不能据此判断代理方向。用户需要明确确认。名称随已关联对象改名同步；删除或解除对象关联后保留案件姓名快照、服务身份及所有流程身份。移除案件当事人只删除本案关系及其各流程身份，不删除独立对象。删除案件先入回收站，恢复保留全部信息。

数据分工：case_parties 保存案件级委托关系与可选对象引用；proceeding_party_roles 按 (party_id, proceeding_id) 保存身份。同案归属、非空与长度校验由 Rust 执行。contact_links.party_id 标记系统维护的反向关联，只维护此当事人自身的关联，不覆盖其他用户手动关联；从对象页解除该关系会同步取消对象引用。

## 1.2 流程模板与非诉业务

workflow_templates 是可编辑、可复用的业务模板，区分诉讼与非诉，内含初始阶段。默认提供一审、二审、再审、执行、合同审查、专项顾问；支持新建、编辑、删除模板，也可不预设阶段。创建流程时填写本次名称、明确选择前序；法院、法官始终可选，非诉默认收起司法信息。

模板与实例分离：proceedings.kind 引用模板标识，name、category 和初始阶段在创建时复制。修改模板只影响以后新建流程；已有流程可独立重命名、调整阶段。删除模板是从候选中归档，不删除既有流程与材料。案件状态、流程生命周期、关注、阶段状态仍相互独立。

数据库版本 6 移除旧 proceedings.kind 固定枚举约束，增加模板、名称快照、当事人与各流程身份。版本 1–5 升级前在线备份；在事务外临时停用外键执行表重建，事务提交前做完整 foreign_key_check，成功或失败都重新启用外键。保留既有流程 ID、前序、阶段、事件、材料、账目及联系人关系，不为旧案件增加新流程或我方身份。版本 3–6 的完整备份仍可校验恢复。
