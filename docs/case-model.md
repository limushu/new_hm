# 案件档案与办理程序

## 业务边界

一个案件档案对应同一委托或争议。档案承载案情摘要、类型标签、当事人、日程、待办、工作记录和收支；内部可以有多个一审、二审、再审、执行等办理程序。同类程序可以重复建立，通过独立 ID、案号和显示序号区分。

程序不是案件状态。看板上的“未开始 / 进行中 / 已结案”等状态属于整个档案，可由用户自定义；某个程序办结不会自动关闭整个档案。

## 三个独立维度

| 维度 | 含义 | 保存位置 |
| --- | --- | --- |
| 案件状态 | 整个委托或争议的管理状态 | cases.status_id |
| 程序 | 一个具体办理过程，有独立案号、法院、法官、材料与阶段 | proceedings |
| 程序内阶段 | 当前程序内部的工作进展，如立案、举证、开庭 | stages，按 position 排序 |

每个程序有“办理中 / 已办结”生命周期。多个程序可以同时办理。每个案件最多指定一个“当前关注”的办理中程序，用于概览和看板摘要；查看另一个程序只是页面浏览，不会修改当前关注。办结当前关注程序后清空关注，用户再自行选择，不推测另一个程序应当接手。

程序内阶段以 stages 的 current 行为准；proceedings.stage 保留旧版兼容摘要。阶段名称允许用户自定义，不硬编码为必须遵循的法律流程，也不根据阶段名称自动结案。已办结程序保留历史，不允许继续切换阶段，恢复办理后可继续调整。

## 办理路径

顶部始终列出本案全部程序，包括历史程序。节点显示当前阶段或已办结、案号，并用关注图标标出当前关注程序。点击节点进入该程序详情。

parent_id 表示用户确认的“承接自”，只能引用本案另一个程序，禁止自引用和循环。多个程序可以承接同一前序程序，表达并行分支。它不是自动推演的诉讼路线，也不是 Git 的提交合并模型；当前每个程序只有一个前序。

新增程序时明确展示前序选项，可选择独立程序。新增的程序成为当前关注，已有程序仍保持原生命周期。旧数据升级后不猜测前序，不根据一审、二审、执行名称拼接假历史。

## 概览与详情

- 概览回答：争议和目标是什么、有哪些程序、当前关注什么、正在做什么、接下来有哪些安排、涉及哪些人、材料如何分布。
- 程序详情回答：这个程序的案号和承接关系、法院和法官、内部办理阶段、程序事项及阶段变更历史。
- 概览中的人员展示本案共用关联及当前关注程序的法院、法官；其余程序的人员在对应程序详情查看。
- 自动阶段切换记录属于历史，默认折叠；人工程序事项单独展示，不让操作日志占据案件首页。

## 共享数据与归档

日历与案件概览读取同一 calendar_events 记录，以 case_id 关联。通用日历创建时不预选案件；从案件详情主动添加时预选当前案件，用户仍可修改或取消。编辑同一日程不复制记录。程序事项仅在用户勾选“同时加入此案件的日历”时生成对应日程，避免把全部操作日志当作日程。

材料归档支持案件共用、具体程序两个正式范围，页面明确标注导入目标。更细的阶段可通过该程序下的文件夹组织；当前没有 stage_id 自动归档，不声称自动跟随阶段移动文件。概览中的范围入口直接打开对应材料范围。

案件类型改为可复用的 #标签。tag_catalog 持久保存用户已创建的名称，case_tags 保存赋予具体案件的关系；移除某案标签或删除该案不会丢失候选名称。旧版固定分类只用于建案程序模板兼容，不再承担用户分类语义。

## 数据升级与校验

数据库版本 5 增加程序生命周期、明确前序、事件分类和标签表。升级前对旧版本建立 SQLite 检查点备份，迁移处于事务内；已有案号、法院、法官和阶段保留，历史前序保持未指定。旧版明确格式的自动阶段事件分类为 stage_change，不删除历史。

后端 hm-core 是规则边界：校验同案承接、禁止循环、标签规范、关注程序生命周期及完成后阶段锁定。React 负责浏览状态和呈现；预览适配器只用于开发，不替代真实 SQLite 迁移验证。
