# 设备日历与通知子系统

2026-11-17，用户同意先接原生系统提醒，再提供可选系统日历入口，并要求把抽象框架作为主要开发目标。1.8.1 已完成公共用例和 iOS 驱动，自动化检查通过；签名内测包正在生成，尚未确认可安装。

## 边界

- `hm-core` 保存唯一业务日程，负责日期、全天安排和提醒时间语义；当前日程沿用设备本地日期时间。
- `hm-application` 的公共通知/日历用例负责生成计划、容量排序、重复协调、改期/删除/恢复、业务身份与系统副本映射。
- `hm-runtime` 的 NotificationDriver / CalendarDriver 定义平台无关契约，能力与权限分别表示。
- 宿主统一观察持久化工作区变更，解锁数据库后协调系统服务；业务页面不直接安排系统通知。
- iOS 驱动对接 UserNotifications / EventKit；桌面通知沿用现有平台插件但迁入公共用例。未接入平台真实返回不可用。

## 通知

用户首次主动保存带提醒的日程或启用系统提醒时请求通知权限；启动和云端接收不弹授权框。拒绝仍保存日程。支持未来系统排程的平台由公共层生成有限窗口，驱动只映射系统 API；桌面即时通知通过相同用例处理到期与送达确认。只协调案笺日程通知命名空间，避免影响其他通知。

日程变化或删除时撤销旧排程；云端应用和备份恢复后重新计算。系统通知的排程成功不等于实际送达，不能将其写作 reminder_deliveries 的已送达记录。通知计划与系统权限属于各设备本地状态。

## 系统日历

用户主动选择单个日程和可写系统日历后建立单向关联；首次使用按系统要求申请授权，并说明仅管理用户选中的案笺日程副本。之后业务日程改期/删除由公共协调器更新对应系统副本。不导入其他个人日历内容，不实现双向编辑回流。

系统标识和关联状态保存在工作区外的本机私有协调文件，不加入案件同步/备份。驱动验证副本确由案笺创建，避免误改或删除无关事件；系统接口不支持跨设备唯一性/原子比较时，不宣称强一致保证。通知提醒由案笺统一处理，创建日历副本不额外复制提醒来造成双重通知。

## 验收

- 公共用例测试覆盖授权拒绝仍可保存、无权限不偷偷请求、重复协调不重复发送/创建、改期/删除/恢复、排程容量、全天日期和附件无关业务变更。
- 检查所有持久化入口共享变更协调，外部调用期间不持有业务 Store 锁。
- iOS 原生测试通过注入系统服务适配器验证请求与归属边界；真实锁屏提醒、系统设置开关、日历写入和改期另在签名真机验收。

## 签名真机验收步骤

1. 新建未来几分钟的日程并选择提醒时间，允许通知；退出到桌面或锁屏，核对提醒。再改期或删除，核对旧时间不再提醒。
2. 在已保存日程中选择“添加到系统日历”，授权并选择目标日历；打开系统日历核对标题、时间，再在案笺改期或删除。全天日程应保持相同业务日期。
3. 拒绝权限后保存日程，确认本机内容仍可查看；在系统设置重新授权并回到案笺，检查状态刷新。
4. 取消系统日历关联后，确认副本保留且后续案笺修改不再维护该副本。个人其他日程不应受到影响。

iOS 系统限制待排通知数量，目前驱动上限为 64，公共层优先安排最近事项并为其他子系统保留已占空间；继续使用应用时补充后续排程。系统排程不保证最终显示，受用户通知设置、专注模式等影响。日历副本是单向、逐设备选择的关联，不意味着其他设备已自动建立关联，也不提供系统日历反向编辑回流。
